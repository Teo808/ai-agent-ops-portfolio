Browser automation preflight

Before an agent clicks inside a real account, it should prove the browser, account, action boundary, and result.

The preflight

Browser automation is only useful when it is acting in the right account, on the right page, with a clear idea of what it is allowed to change.

  1. Confirm the browser context. Check the URL, page title, visible account signals, and whether the tab is a real target tab instead of a blank or extension page.
  2. Confirm the account. Use the profile menu, workspace name, store name, candidate profile, or other page proof before making a change.
  3. Confirm the action boundary. Know whether the agent may draft, upload, submit, send, publish, or only save for review.
  4. Check for real blockers. Retry normal friction, but stop for CAPTCHA, two factor login, legal consent, sensitive personal data, payment requests, assessments, or questions that would require guessing.
  5. Verify the result. Look for a confirmation page, permalink, activity page, upload success message, or portal status before claiming success.
  6. Leave a clean handoff. Record what was tried, what changed, what is still open, the blocker, and what the next run should check first.

What I watch for

A launch command is not proof of control. The agent needs page level evidence.

A signed in site still needs account proof before a send, submit, or publish click.

A failed upload is usually friction first. CAPTCHA, legal consent, and sensitive data are stop signs.

If the result is not visible afterward, the honest status is unverified.

Why this matters

The risky part of browser automation is not opening the page. It is acting with confidence when the context is wrong or the result was never verified.

This checklist is a small way to keep agent workflows useful for support, QA, operations, and implementation work. It protects the user, and it gives the next person enough state to continue without starting over.
