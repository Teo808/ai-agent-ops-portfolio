Real-account automation incident runbook

A one-page runbook for the moment an agent workflow touches a real account but the browser session is not proven safe.

The incident

Some workflows are safe to keep running locally. Real-account workflows are different. If the next step is a post, DM, job application, recruiter message, file upload, or submit button, the agent needs proof of the browser, the account, the action boundary, and the result path.

If that proof is missing, the right move is not to click harder. The right move is to write the incident clearly, block risky actions, and leave the next repair step obvious.

The runbook

  1. State what failed. Name the exact tool call, page, account proof, or confirmation step that failed.
  2. Scope what is blocked. Block sends, posts, follows, applications, uploads, and messages until verification returns.
  3. Keep the evidence small. Log the exact error, last safe page, visible account proof status, and duplicate-contact risk.
  4. Choose the safe decision. Stop, stage, save, or continue only with local proof work that does not touch the account.
  5. Give the repair path. Reload the browser tool, start a fresh session, or restart the gateway, then verify the target account before acting.
  6. Resume carefully. Check recent outreach and application history before sending anything from the recovered session.

Example incident table

Evidence Status Decision
Browser tab call timed out before account proof Active session not verified Block LinkedIn, X, job portal, and email account actions
Separate health test can list tools Repair clue only Do not treat this as permission to post or submit
Latest application target already received outreach Duplicate-contact risk exists Wait, or find a new safe target after verification returns
Local portfolio work is available Safe fallback Create proof, save a draft, and log the blocker honestly

Resume checklist

  • Open the recovered browser in the same real account path, not a sandbox or copied session.
  • Verify the target page, visible account, and allowed action before clicking anything public.
  • Check the latest application, message, and comment history so the workflow does not double-contact someone.
  • Take one small action first, then capture the visible receipt before doing the next one.

Why this is useful

It stops fake success claims when the active session cannot prove a real account.

It protects recruiter and company relationships from duplicate or unsafe messages.

It gives support a clean recovery note instead of a vague browser failure.

It turns blocked automation into safe proof while the account path is repaired.

Run it

python demo/real_account_incident_runbook.py --all

The first example returns "BLOCK_REAL_ACCOUNT_ACTIONS_AND_DO_LOCAL_PROOF." That is the honest decision when the active browser session is not verified, even if another health check says the tool exists.
