Featured case study / Reliability

I don't call a browser workflow healthy just because it launched.

A scheduled real-account workflow kept reporting that Chrome was locked. The useful answer was not to retry harder. It was to prove which processes owned the profile, protect the user's normal browser, remove only stale scheduled owners, and verify the profile was actually free.

Incident

Multiple automation owners shared one scheduled profile.

The browser route reported "already in use" before it could inspect a tab. A retry could have interrupted another run or touched the wrong Chrome session.

Result

Stale owners removed. Zero matching processes remained.

Normal Chrome was left alone. The scheduled profile was isolated, cleaned, and verified before another run was allowed to use it.

What I investigated

  • Reproduction: The same profile-lock error appeared across application, outreach, and portfolio runs.
  • Ownership: Windows process command lines showed several Playwright MCP processes pointing at the same scheduled user-data directory.
  • Boundary: The user's ordinary Chrome windows used different processes and were not treated as disposable automation state.
  • Verification: After targeted cleanup, a second process query returned zero matching scheduled Chrome or MCP owners.

The investigation pattern

1. Read the errorCapture the exact profile path and the stage where the workflow stopped.
2. Trace ownershipInspect process names, parent processes, command lines, and start times.
3. Protect the boundaryTarget only the scheduled profile. Never kill a normal account session by assumption.
4. Prove recoveryQuery again and require zero matching owners before calling the route healthy.

Operator receipt

{
  "symptom": "scheduled browser profile already in use",
  "scope": "Copy A scheduled automation only",
  "risk": "interrupting a normal signed-in Chrome session",
  "evidence": "multiple stale MCP owners shared one profile",
  "action": "stopped exact scheduled owners only",
  "verification": "remaining matching processes: 0",
  "claim": "profile is free for a fresh scheduled run"
}

This is the difference between a plausible fix and an auditable one. The receipt says what was observed, what boundary was protected, what changed, and what was verified afterward.

Why this matters in AI agent operations

Agents often fail at the environment boundary, not the model boundary.

A retry can be riskier than a pause when real accounts are involved.

Support needs a reproducible diagnosis, not a confident guess.

Good handoffs leave the next operator a safe resume check.

The qualification this demonstrates

I can move from a vague automation failure to a scoped diagnosis, a safe repair, and a verification receipt. That is the work between an agent demo and a dependable workflow in a real environment.
